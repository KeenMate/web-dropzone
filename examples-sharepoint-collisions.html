🗂️ SharePoint-style name collision

Check filenames against a server inventory before upload — let the user choose Overwrite / Rename / Skip per file

SP01 · What this demonstrates

This is the flow a SharePoint / OneDrive document library uses when you drop files into a folder:

  1. The user drops files onto the zone.
  2. Before any bytes leave the browser, the page POSTs the filenames to the server and asks "do any of these already exist?"
  3. For each collision, the user picks an action per row: Overwrite, Rename (with a suggested non-conflicting name), or Skip.
  4. Once every collision has a decision, the upload starts. Renamed files upload under the new name.

No core API changes were needed for this — it's a straight application of mode="structural" (custom per-row rendering), auto-upload="false" (stage instead of upload-on-add), removeFile(id) (skip), and a closure-captured decisions map (read by both the row renderer and the uploadFileCallback).

SP03 · How the wiring works

Three pieces:

1. A side Map holds the user's decision for each colliding file. It's keyed by FileState.id and updated by the per-row UI. The framework doesn't need to know it exists — the upload callback closes over it.

const decisions = new Map() // fileId -> { action: 'pending'|'overwrite'|'rename', renameTo? }

2. files-changed drives the collision check. Every time a file is added we ask the server, then either seed the decisions map with 'pending' (collision) or leave the file untracked (new — will upload as-is).

dz.addEventListener('files-changed', async (e) => {
    const newFiles = e.detail.files.filter(f => !seenIds.has(f.id))
    if (!newFiles.length) return
    const report = await checkNames(newFiles.map(f => f.name))
    for (const file of newFiles) {
        seenIds.add(file.id)
        const exists = report.find(r => r.name === file.name)?.exists
        if (exists) decisions.set(file.id, { action: 'pending', renameTo: suggestRename(file.name) })
    }
    refreshToolbar()
})

3. The row renderer reads the decisions map and re-renders itself when the user clicks. Element-returning renderFileItemCallback means each row owns its own DOM and event listeners; no need to bother the framework when local state changes.

dz.renderFileItemCallback = (file) => {
    const row = document.createElement('div')
    const repaint = () => {
        const d = decisions.get(file.id)
        row.innerHTML = renderRowHtml(file, d)
        row.querySelector('[data-action=overwrite]')?.addEventListener('click', () => {
            decisions.set(file.id, { action: 'overwrite' }); repaint(); refreshToolbar()
        })
        // … rename, skip buttons …
    }
    repaint()
    return row
}

4. The upload callback closes over the decisions map. The first arg is the native File; we find the matching FileState to pull its id, then send the right thing. Returning { name } renames the file in the UI on success.

dz.uploadFileCallback = async (rawFile, onProgress, signal, ctx) => {
    const fileState = dz.files.find(f => f.file === rawFile)
    const decision  = decisions.get(fileState.id)
    const finalName = decision?.action === 'rename' ? decision.renameTo : rawFile.name
    // …simulated upload progress…
    SERVER_INVENTORY.add(finalName) // server now knows about it
    if (decision?.action === 'rename') return { name: finalName }
}
